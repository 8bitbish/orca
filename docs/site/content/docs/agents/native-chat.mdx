Chat UI is an experimental view layered on supported agent terminal sessions. The terminal remains the source of truth; Chat UI is a structured transcript + composer for the same PTY. Transcript decoding covers **Claude**, **Codex**, **Grok**, and **OMP** — OMP sessions open in Chat UI like the others instead of staying raw-terminal-only.

## Enable

1. Open **Settings → Experimental → Chat UI**.
1. Turn **Chat UI** on.
1. Optionally set **Default view** to **Chat UI** so new supported agent tabs open in chat; keep **Terminal** to open the TUI first.

Toggle Chat UI ↔ terminal from the agent pane once enabled.

## Composer

- Type a message and send (or stop a working turn). Attach files/images when the host supports it. Unsent draft text and attachments stay with the pane across disconnect/reconnect when the host can restore them. A settled transcript also stays on screen while the same session reconnects, instead of blanking until the fresh load finishes (desktop and mobile share that retention).
- Type `/` for slash commands and discovered **skills** (filtered per agent when possible). The slash catalog is agent-aware (Claude vs Codex command sets) and shared with mobile Chat UI.
- Use the **model** and options pills (thought level, mode, agent-specific session options) when the agent exposes them. **Claude** model choices come from the **installed Claude CLI on that host** (not a hardcoded list), so new models show up after you update the CLI. **Codex** supports direct model selection from the pill (sends `/model <id>`), with bare `/model` still opening the agent picker. **Grok** exposes **model** (`-m` at launch, `/model` mid-session) and **reasoning effort** (`--reasoning-effort` at launch, `/effort` mid-session); the model list is probed from the signed-in Grok CLI (`grok models`) so retired ids drop out of the picker. Effort choices follow the selected model: Grok 4.6 includes **Extra high**, while Grok 4.5 stops at **High**. **Before the agent process starts**, the composer can show draft launch options that apply on first start; after the session is live, pills that only affect a running turn stay disabled or labeled until the session is ready. Live values go to the CLI in that tab.

## Questions from the agent

When Claude shows an **AskUserQuestion** (or similar structured permission/question card), Chat UI should render the question card in the transcript so you can answer from the composer path instead of treating it as a collapsed tool call. Confirm with **Submit** on the card. That includes agents running on a paired [Remote Orca Server](/docs/remote-servers) / headless host — not only local panes.

## Replies

- The agent's reasoning folds to one line: **Thinking…** while it is the turn's newest output, then **Thought for 12s** (or **Thought** when no duration can be derived from the session's timestamps). Click it, or focus it and press Enter or Space, to read the full reasoning. Claude Code records its thinking without the text, so for Claude the line usually has nothing to open; back-to-back thoughts share one line.
- A reply can include diagrams as fenced blocks. A `mermaid` fence renders as a diagram in the app's colors. `html` and `svg` fences render as a live preview in a sandboxed frame, which has no network access and cannot run the reply's scripts. Each diagram has a **Code** toggle to show its source and a copy button. A fence renders once it is complete; while it is still streaming it shows as code.
- A `widget` fence renders as a static visual, the way Claude.ai shows its inline widgets: a quiet **Widget** line whose chevron reveals the source, a copy button, and the visual on a rounded card. It uses the same sandboxed frame, so nothing in it runs or reaches the network. Every preview carries a built-in style kit that follows the app theme in light and dark: cards (with an accent for the recommended option), badges, key-value price rows, totals and deltas, legends, Gantt timelines, callouts, device frames, dashed guides and measurement arrows. The [`visualize` skill](/docs/cli/skills#visualize) teaches Claude the class names and when a visual beats prose.
- A reply can show Orca projects live. A link with the `orca-worktree:` scheme, such as `[orca-personal](orca-worktree:orca-personal/personal)`, renders as a **project chip**: a small pill with the project's icon, its name, the workspace name (unless it is the main one) and a status dot. Click it to focus that workspace. The target is `repo/workspace` by display name, a bare `repo` for its main workspace, or a worktree id; one Orca does not know reads as plain text, and only Chat UI replies draw chips (everywhere else the link stays plain).
- A ` ```project-card ` fence renders as a **project card**: the project's icon, name and workspace, a status pill (**Working**, **Needs you**, **Done**, **Idle**, or **Unverifiable** when Orca cannot reach the SSH host or has stopped hearing from the agent), the assistant's `note`, a live line with the agent's current tool or last message and how long ago, the assistant's `ask` highlighted, and an **Open** button. The status and live line come from the same agent status the sidebar and `orca worktree ps` read, and keep updating after the reply is sent; the note and ask stay as written. The fence holds JSON:

  ```json
  {
    "worktree": "ImageReview/packaging",
    "note": "Testing a fix in fixtest.py",
    "ask": "The commit skipped the pre-commit hook. Fix pnpm first?",
    "actions": [
      { "label": "Fix pnpm first", "reply": "Fix pnpm in ImageReview/packaging, then re-run the hook", "style": "primary" },
      { "label": "Reply…", "input": true }
    ]
  }
  ```

  Use `project-card` as the whole info string: Chat UI reads only the first word of a fence's info string, so ` ```widget project-card ` renders as a widget. Bad JSON or an unknown workspace shows the fence as a code block.
- A card's **actions** are reply buttons, up to four. Each shows the exact text it will send; `"input": true` opens a small text box instead. Clicking one sends that text into the same chat as your next message, exactly as if you had typed it, and disables the card's actions. Nothing is clicked or run automatically. Orca does not write to the agent's transcript, so after a reload it reads which action you chose from the transcript itself (a later message of yours that matches the action's text); a typed reply is remembered locally on this device. The project icon is the card's own `icon`, else the icon the sidebar shows for the repo (one you picked in its settings, or the favicon or GitHub avatar Orca found when you added it), else the app icon found in a local repo (an Xcode `AppIcon.appiconset`, `build/icon.png`, `resources/icon.*`, `public/favicon.*`, then Orca's usual repo icon files), else a coloured letter. Chips use the same icon. SSH and remote projects never get an app icon, since Orca does not read remote files for one, but they do get their sidebar icon. The mobile app does not draw chips or cards; it shows the fence as its raw block.
- When to use them, as the `visualize` skill tells Claude: a chip for any project mention, a card for an update about a project, and actions only when you have a decision to make.
- A finished `bash`, `sh`, `zsh`, `shell` or `console` fence in the agent's reply (or an unlabelled one whose every line is plainly a command) has a **Run** button. It never appears in your own messages, tool output, reasoning or a fence still streaming. Run types the whole block, as one script, into a **Runs** tab in the chat's workspace: one per workspace, reused, added without switching to it or taking focus. The block runs under the shell its fence names (`shell`, `console` and unlabelled use bash, else sh), on the machine that runs that workspace, including an SSH host. A first line of `# workspace: <repo/workspace>` runs it in that workspace instead, shown as its project chip; a workspace Orca does not know, an SSH host that is not connected, or Windows without Git Bash disables Run and says why. `console` blocks run only their `$ ` lines.
  - Under the block, a fixed-height pane shows the run's output live with its colours. It follows new output while you are at the bottom and stays put if you scroll up; it never takes typing. The status reads **Running…**, then a tick or cross with the exit code and how long it took, measured between the run's own start and end markers. **Stop** interrupts it (as Ctrl+C would) and **Run again** reruns it; a block cannot be started twice at once, and one workspace's Runs tab runs one block at a time.
  - **Needs input** appears when the last line asks for a password, a yes/no answer or a key press, or ends like a prompt and the run has gone quiet for a moment. Orca cannot see whether the process is blocked reading the keyboard, so this is read from the output. **Go to terminal** (or **Open in terminal**) focuses the real Runs tab, where you answer.
  - The last run of each block, with its status and the last 200 lines of output, survives a reload. A run Orca lost sight of (it reloaded mid-run, the stream ended without the run's end marker, or Stop was never confirmed) reads **Unverifiable**, never failed.
  - Blocks that can do damage ask first, in a dialog naming each risk with the command that raised it and showing the whole block: `sudo`, deletes, `git push` and history rewrites, `--force`, package installs, `npx`, Docker removals, Keychain use, anything that sends data off the Mac (uploads, `scp`, `rsync` to a host, `gh` writes, publish and deploy), cloud CLIs, file overwrites, `kill`, `launchctl`, `defaults write`, `osascript`, disk tools, and anything the check cannot read with confidence (`eval`, `exec`, `source`, `sh -c`, `python -c`, command names built at run time, decoded text piped onward, pipes into a shell, aliases and functions). The rules are fixed in Orca; nothing in a chat can change them, and only your click on the button runs a block.

## Availability

Chat UI ships on desktop for supported local and remote (paired server) agent sessions. The [mobile companion](/docs/mobile) reuses chat-style transcript patterns for the same paired sessions.

  TUI when you need every OSC/status detail.
